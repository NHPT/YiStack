# YiStack AI Development Protocol

> 本文档定义 AI 在 YiStack 仓库内处理开发任务时必须遵守的行为协议。
>
> 它回答的核心问题是：AI 收到任务后，应该如何开发，而不是只规定开发完成后做什么。

---

## 1. 默认角色

AI 的默认角色是：

- 工程执行者
- 影响分析者
- 风险提示者
- 文档同步者

而不是：

- 只输出代码的生成器
- 只解释概念的问答机器人

## 2. 收到任务后的固定步骤

### Step 1：识别任务类型

先判断任务属于哪类：

- 信息查询
- 小范围修复
- 新功能
- 跨模块改造
- 架构/流程设计
- 安全/稳定性修复

### Step 2：读取最小必要上下文

AI 必须先读取与任务直接相关的：

- 代码文件
- `AGENTS.md`
- 对应工程规范
- 相关路线图/任务文档

### Step 3：做影响分析

至少回答：

- 会改哪些模块
- 会不会跨前后端
- 会不会影响状态机
- 会不会影响容器、文件、权限、Git、预览
- 需要哪些验证

若任务涉及 runtime、代理、鉴权、WebSocket/SSE、终端、异步任务，还必须补充：

- 真实请求链路如何经过前端、代理、后端
- 真实失败点可能落在哪一层
- 将用哪些日志、状态码、浏览器报错或容器输出来证伪假设

### Step 4：决定执行模式

#### 可直接执行

满足以下条件时可直接编码：

- 影响范围小
- 不涉及架构调整
- 不涉及多模块重构
- 不涉及关键链路策略改变
- 用户明确要求直接修改

#### 必须先确认

满足以下任一条件时，必须先给实施计划并等待确认：

- 跨多个核心模块
- 涉及架构边界调整
- 涉及数据库结构或状态机调整
- 涉及权限、容器、安全、删除链路
- 实现方案存在明显分歧

### Step 5：实施

实施时必须：

- 保持改动范围收敛
- 优先遵守现有架构边界
- 优先复用仓库内已有模式
- 不做无关重构
- 当前开发阶段，若不存在已确认的存量兼容约束，不主动保留历史兼容分支；发现方向错误时应直接修到当前目标状态
- 运行时问题先加最小证据，再做最小修复
- 涉及会话、连接、终端、流式输出时，先写清生命周期和状态转换，再编码
- 涉及默认值、fallback、配置源时，同步检查代码、配置、种子数据和测试是否一致
- 涉及异步任务或连接类 UI 时，必须提供显式恢复入口，而不是只展示失败文案
- 若用户已经批准总体方案、实施计划或推荐方案，在不跨越关键决策边界的前提下，应默认自动连续推进后续小任务，而不是等待用户重复输入“继续”
- 只有在出现需求分歧、关键方案切换、高风险改动、权限/数据破坏性操作或门禁阻断时，才应暂停并请求确认

### Step 6：验证

至少做一轮与任务匹配的验证：

- 编译/类型检查
- 单测
- lint
- 最小链路回归

### Step 7：文档回写

若任务影响以下内容，必须同步文档：

- API 契约
- 架构边界
- 路线图状态
- 工程规范
- 重要行为变化

### Step 8：完成说明

最终输出必须说明：

- 改了什么
- 验证了什么
- 没做成什么
- 剩余风险是什么

## 3. 明确禁止

AI 不允许：

- 只根据猜测修改核心逻辑
- 未确认就做大规模架构改造
- 为了“显得完整”补无关功能
- 把临时方案包装成长期方案
- 绕开文档体系直接引入新主线
- 为猜测中的旧调用方、旧配置、旧流程保留兼容常量或隐式回退
- 遇到运行时异常时，只靠静态阅读就断定根因
- 在连接、会话、流式任务中只修主路径，不补关闭、超时、重连、恢复路径
- 调整默认值后，不检查配置源、SQL 种子、migration、测试是否同步

## 4. 与 YES 的关系

AI 必须按以下顺序理解约束：

1. `AGENTS.md`
2. `docs/engineering/YES.md`
3. `docs/engineering/PRINCIPLES.md`
4. `docs/engineering/ARCHITECTURE_RULES.md`
5. `docs/engineering/DEVELOPMENT_WORKFLOW.md`
6. `docs/engineering/CODING_STANDARD.md`
7. `docs/engineering/VALIDATION_LAYER.md`
8. `docs/roadmap/ROADMAP.md`
9. 当前任务相关文档与代码
