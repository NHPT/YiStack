# YiStack Development Workflow

> 本文档定义 YiStack 的标准开发流程。
>
> 目标不是增加流程负担，而是避免 AI 与人工协作时跳步、漏步、跑偏。

---

## 1. 适用范围

本流程适用于：

- 新功能
- 跨模块重构
- 核心链路 bug 修复
- 架构调整
- 数据结构、状态机、接口契约调整

对于极小修复，可以简化步骤，但不能跳过“影响分析”和“验证”。

## 2. 标准流程

### Step 1：需求澄清

先确认：

- 目标是什么
- 不做什么
- 验收标准是什么
- 是否属于当前路线图范围

如果需求本身不清晰，不允许直接编码。

若任务属于以下任一情况，还必须先执行 Foundation Design（历史别名：Bootstrap Design）：

- 新项目启动
- 新业务域启动
- 需要先冻结用户/权限/状态机/契约等高成本基础决策
- 若后置将显著增加重构成本的工程基础设计

Foundation Design 的输入框架见：

- `docs/engineering/YES_BOOTSTRAP_FRAMEWORK.md`

### Step 2：上下文读取

至少读取：

- 相关代码
- `AGENTS.md`
- 相关工程规范
- 相关架构文档
- 当前阶段路线图与任务文档

不能只根据聊天上下文直接改代码。

### Step 3：影响分析

明确列出：

- 影响模块
- 影响接口
- 影响状态
- 影响数据库/容器/文件/Git/预览
- 可能回归点

若任务涉及以下任一链路，还必须额外列出“运行链路清单”：

- 容器 / runtime
- 鉴权 / 权限
- 反向代理 / 跨域 / Origin
- WebSocket / SSE / 流式输出
- 定时任务 / 异步任务 / 长连接

运行链路清单至少回答：

- 请求从哪里发起
- 中间经过哪些转发层
- 最终落到哪个 handler / service
- 失败会表现成什么状态码、日志或前端症状

若影响跨前后端或跨多个核心模块，必须进入“计划确认”。

### Step 4：实施计划

非琐碎任务必须先输出实施计划，至少包含：

- 修改范围
- 执行顺序
- 风险点
- 验证方式

若任务属于多阶段 AI 执行链路，计划中还必须补一份“可展示阶段计划”，至少说明：

- 预计分为几个阶段
- 每个阶段的目标与主要任务
- 当前处于哪个阶段
- 当前阶段正在执行哪个任务
- 哪些条件会导致阻塞
- 阶段切换和完成应如何向用户展示

若用户已经批准总体方案、实施计划或推荐方案，后续默认执行策略还必须说明：

- 哪些子任务会自动连续推进
- 哪些节点仍需要用户确认
- 什么情况下必须中断自动推进并升级为确认

若任务属于运行时问题或真实环境异常，计划中还必须包含：

- 先收集哪些证据
- 用什么最小方式定位失败点
- 哪些日志 / 状态码 / 运行输出来判断修复是否生效

计划未经确认，不进入大规模编码。

## 3. 编码顺序

默认实现顺序如下：

需求/问题确认  
↓  
影响分析  
↓  
方案与边界确认  
↓  
数据模型 / 状态机  
↓  
Repository  
↓  
Service  
↓  
Handler / API  
↓  
Frontend  
↓  
联调验证  
↓  
文档回写  
↓  
提交收尾

说明：

- 不是所有任务都必须改全链路
- 但一旦涉及全链路，默认顺序应遵守上面的依赖方向
- 涉及会话、连接、终端、流式任务时，必须在编码前补一份状态机 / 生命周期说明
- 若总体计划已获批准，同一计划下的连续子任务默认自动推进，不应要求用户为每个小任务重复输入“继续”

## 4. 禁止事项

禁止以下行为：

- 未读上下文直接编码
- 未做影响分析直接跨模块修改
- 未收集运行时证据就修改运行时核心逻辑
- 直接在 `handler` 中堆业务逻辑
- 先改前端状态，后补后端契约
- 只改运行路径，不补错误路径
- 只做成功路径，不做异常恢复路径
- 改默认值但不检查配置源、种子数据和测试是否一致
- 跳过验证就宣称完成
- 不更新相关文档

## 5. 完成定义

一个任务只有满足以下条件才算完成：

1. 目标代码已落地
2. 相关回归点已检查
3. 必要验证已执行
4. 必要文档已更新
5. 最终结果与用户请求一致

“代码写完”不等于“任务完成”。

对以下类型任务，还必须额外满足：

- 运行时 / 连接类任务：至少完成一次真实链路验证
- 会话 / 终端 / 流式任务：至少验证创建、异常、关闭、恢复四种状态
- 默认值 / 策略调整：至少确认代码、配置、种子、测试没有继续漂移

若任务修改了 AI 多阶段执行体验，还必须额外确认：

- 用户看到的阶段与系统真实阶段一致
- 用户看到的当前任务不是猜测文案，而是结构化状态映射
- 阻塞原因、完成项和下一步动作在 UI 中有明确表达
- 已批准计划下的自动推进边界清晰，且只有在关键决策点、风险点或门禁阻断时才会暂停请求确认
