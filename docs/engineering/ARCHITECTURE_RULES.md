# YiStack Architecture Rules

> 本文档定义 YiStack 当前阶段必须遵守的架构边界规则。
>
> `ARCHITECTURE.md` 负责描述架构设计与推荐实现；
> 本文档负责定义“开发时不能越过的边界”。
>
> 本文档属于 YES Engineering Kernel 的 Architecture Layer。

---

## 1. 总体规则

- 优先保持前后端清晰分层
- 优先保持业务编排与基础设施调用分离
- 优先保持项目文件、运行时、Git、消息、权限等领域边界清晰
- 新增能力时优先放到现有边界内，而不是引入新的混合层

## 2. 后端调用方向

允许的主要依赖方向：

`handler -> service -> repository/pkg`

补充说明：

- `handler` 可以依赖 `service` 和协议层 DTO
- `service` 可以依赖 `repository`、`pkg` 与必要模板资源
- `repository` 只负责持久化，不承载业务编排
- `pkg` 只负责通用能力，不承载具体业务规则

## 3. 明确禁止

### Handler

`handler` 禁止：

- 直接写复杂业务流程
- 直接拼接多个 repo 完成完整业务
- 直接做容器编排、Git 编排、文档写入等长链路业务决策

### Repository

`repository` 禁止：

- 直接访问 runtime / container / HTTP
- 承担权限决策
- 承担流程编排

### Runtime / Container

运行时与容器相关模块禁止：

- 直接处理 HTTP 协议细节
- 直接感知前端展示状态
- 越过服务层操作业务语义

### Prompt / Template

提示词与模板资源禁止：

- 直接调用数据库
- 直接调用 runtime
- 承担业务编排逻辑

## 4. 前端规则

- 页面负责组织交互，不承载过多协议拼装与业务决策
- API 契约转换优先收敛在 `lib/` 和相关 helper 中
- UI 状态必须和后端真实状态保持一致，避免长期使用前端虚构状态
- `Workspace` 相关改动必须特别关注：消息流、文件树、编辑器、Git、预览的一致性

## 5. 状态机与契约

涉及状态值时，必须同时检查：

- 数据库约束
- 后端状态机
- 前端类型与 UI 分支
- API 返回值

不允许只改一层。

## 6. 文件、容器与 Git

以下能力默认应在项目运行环境内完成：

- 文件树读取
- 文件内容读取
- 文件写入/删除/重命名
- Git 提交/历史/diff/回滚
- 与项目代码直接相关的命令执行

宿主机只保留平台底座职责，例如：

- 容器创建/启动/停止/删除
- 项目元数据与数据库
- 平台级状态文件与基础设施管理

## 7. 新模块引入规则

新增模块前，先回答：

1. 它属于哪个现有边界
2. 为什么现有模块无法容纳
3. 它的输入输出契约是什么
4. 它如何验证不会扩大耦合

回答不清楚时，不应新增模块。
